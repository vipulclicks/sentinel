# Honest Exception Report — Held-Out Test Set

This is not a cherry-picked demo. Every number and case below comes from the
**same held-out test set** used in `src/train.py` (`random_state=42`, 25%
split, untouched during training). Generated by `src/extract_demo_cases.py`.

## Summary
| Metric | Value |
|---|---|
| Held-out test set size | 12,839 transactions |
| True positives (correctly caught fraud) | 335 |
| False positives (flagged, actually legit) | 25 |
| False negatives (missed fraud) | 3 |
| True negatives | 12,476 |
| Precision | 93.1% |
| Recall | 99.1% |

## Why the 25 false positives happened
Every false positive shares two traits: it's a `TRANSFER` or `CASH_OUT`, and it's
the **first-ever transaction to that destination account**. Two sub-patterns:

- **High-ratio CASH_OUTs** (e.g. ₹15,854.83 draining 93.8% of a ₹16,904 balance
  to a brand-new destination) — indistinguishable, from a single transaction's
  features alone, from a genuine large withdrawal to a new account.
- **Mid-size TRANSFERs to new destinations** (₹550–₹1,750 range, 11-24% of
  balance) — these look like the early stage of a mule fan-out, but in this
  batch are legitimate one-off payments.

**Root cause:** the model currently weighs "new destination + balance drain"
heavily, because that's genuinely the strongest signal in the training data —
but it can't yet distinguish a first-time legitimate payee from a first-time
mule account using single-transaction features alone.

**What would fix it:** account/payee-level historical trust scores (e.g. "has
this destination received money from other users before, and were those
flagged"), which needs graph-level features beyond this project's scope.

## Why the 3 false negatives happened
All 3 are `TRANSFER`s with a **moderate** balance-drain ratio (23-26%), well
below the typical fraud signature (usually 70%+). These are individual
transactions from a "rapid mule fan-out" burst pattern, where each transfer
looks unremarkable on its own — the tell is the *velocity* (many transfers to
different mule accounts within minutes), not the individual transaction size.

**Root cause:** the velocity features (`txn_count_5min`, `txn_count_60min`)
exist in the model, but a transaction near the *start* of a burst hasn't
accumulated enough prior-transaction history yet to trigger the velocity
signal — a cold-start blind spot within the burst itself.

**What would fix it:** a lookahead/batch-level pass that re-scores early
transactions in a burst once the full burst is visible, rather than scoring
each transaction independently in real time.
